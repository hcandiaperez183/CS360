# CS360
Students will apply mobile development principles and best practices to develop mobile applications using user-centered design principles and industry standards. Upon completion of a fully-functional mobile application, students will conduct security, product assuredness, and compatibility checks before launching the application.


Briefly summarize the requirements and goals of the app you developed. What user needs was this app designed to address?
- The goal of this project was to build a fully working event tracking app. The app needed a login system where users could sign in or create a new account, with their information saved in a database. It also needed a SQLite database to store events, and users had to be able to add, view, edit, and delete events, with all of them shown in a grid. Last, the app had to ask for permission to send SMS notifications and keep working normally if the user said no.
  The main user need was simple, where people want one place to see their upcoming plans and a way to make sure they don't forget them. Event Tracker solves this by keeping all events sorted by date and sending a text reminder when an event is less than 24 hours away.

What screens and features were necessary to support user needs and produce a user-centered UI for the app? How did your UI designs keep users in mind? Why were your designs successful?
- The app uses a few main screens, starting with the login screen, which lets users sign in or create a new count. The app also includes an event grid, which shows all events sorted by date so the next one is always easy to find. The add/edit event screen lets users enter or change an event's name, date, time, and description. Lastly, the SMS permission screen explains why the app wants to send texts before asking for permission.
  I kept users in mind by making each screen have one clear job and keeping the layouts simple. Buttons are labeled clearly, the most important information is easy to see, and users can get to any feature without going through extra screens. I also explained the SMS permission before asking for it so users understand why the app needs it. The designs were successful because a new user can figure out how to use the app without instructions, and the app still works for every user no matter what they choose for permissions.

How did you approach the process of coding your app? What techniques or strategies did you use? How could those techniques or strategies be applied in the future?
- I built the app in small pieces and made sure each part worked before moving on. I started with the login and account creation, then the database, then the event grid and the add, edit, and delete features, and finally the SMS reminders. This made problems much easier to find because I knew they were most likely the part I had just added.
  I also tried to keep my code clean and easy to read. I used clear names for variables, methods, and classes, kept classes short and focused on one job, and added comments to explain what the code is doing. For security, passwords are stored as salted hashes instead of plain text.
  In the future, I can use the same approach on any project. Building and testing one feature at a time keeps big projects manageable, and writing clean code makes it easier for me or someone else to come back and update it later.

How did you test to ensure your code was functional? Why is this process important, and what did it reveal?
- I tested the app often using the Android Emulator in Android Studio. I checked that logging in worked with correct and incorrect passwords, that new accounts were saved, and that events could be added, edited, and deleted. I also closed and reopened the app to make sure the data was still there. For the SMS feature, I tested both granting and denying the permission to make sure the app worked either way.
  Testing is important because code that looks right doesn't always work right. It showed me problems I would have missed, like making sure the grid updated after an event was changed and that the app didn't crash when the SMS permission was denied.

Consider the full app design and development process from initial planning to finalization. Where did you have to innovate to overcome a challenge?
- The biggest challenge was the SMS feature. I had to make sure the app kept working if the user denied the permission, so I separated the SMS code from the rest of the app and checked the permission before trying to send anything. Android 12 also changed how apps access the SMS service, so I added a check for the Android version so the app uses the correct method on each one. I also marked telephony as optional in the manifest so the app can still be installed on devices without a phone plan, like tablets.
  While writing the launch plan, I also learned that Google Play limits which apps can use SMS permissions. If I publish the app later, I plan to switch to standard Android notifications, which don't need any special permission.

In what specific component of your mobile app were you particularly successful in demonstrating your knowledge, skills, and experience?
- I was most successful with the database and the event grid. I set up the SQLite database to store both user accounts and events, and made sure all of the create, read, update, and delete features worked and that data stayed saved after the app was closed. Connecting the database to the grid so it always showed the latest events took a lot of work, and getting it working well shows what I learned about building a full app from start to finish.
